1. GET/POST /api/fcm-token — UNCHANGED, restated for completeness
================================================================================

POST /api/fcm-token
  Auth: Bearer token (auth:sanctum)
  Body: { "fcm_token": "string (required)", "device_type": "android|ios|web (optional)" }
  Response (verified, real shape):
    { "data": null, "status": 200, "message": "تم حفظ توكن الإشعارات بنجاح." }
  Calling this twice with the same fcm_token is safe — it updates the existing
  row (matched on fcm_token, which is globally unique), it does not duplicate
  and does not error.

================================================================================
2. DELETE /api/fcm-token — NEW, call this on logout
================================================================================

  Auth: Bearer token (auth:sanctum) — token of the user who is logging out
  Body: { "fcm_token": "string (required)" }
  Response:
    { "data": null, "status": 200, "message": "تم حذف توكن الإشعارات بنجاح." }

  This only deletes the row if it belongs to the calling user AND matches the
  given fcm_token — it will not delete another user's row even if you somehow
  sent their token string. It always returns 200 whether or not a row actually
  existed (treat it as "make sure this token is gone", not "assert it existed").

  Call this exactly once, right before/at logout, with the same fcm_token value
  you last registered on this device. If you don't call this, the next person
  who logs in on the same phone will keep receiving the previous user's pushes
  until they overwrite the row with their own POST /api/fcm-token call.

3. NOTIFICATION HISTORY ENDPOINTS — ALL NEW
================================================================================

All require Auth: Bearer token (auth:sanctum). All operate on the CALLING
user's own notifications only — there is no way to read or mutate another
user's notification through these endpoints (verified: cross-user attempts
return 404, never 200).

--------------------------------------------------------------------------------
3.1 GET /api/notifications
--------------------------------------------------------------------------------
  Query params:
    page       optional, standard Laravel pagination
    per_page   optional, default 15
    unread     optional, pass unread=1 to return only unread items

  Response shape (real, from a local test run):
    {
      "data": {
        "data": [
          {
            "id": 1,
            "title": "اختبار",
            "body": "رسالة اختبار",
            "type": "test",
            "data": { "type": "test", "id": "1" },
            "is_read": false,
            "created_at": "2026-08-17 17:03"
          }
        ],
        "pagination": {
          "total": 1,
          "count": 1,
          "per_page": 15,
          "current_page": 1,
          "last_page": 1
        }
      },
      "status": 200,
      "message": "Notifications retrieved successfully."
    }

  Ordering: newest first (by internal id, which is monotonically increasing —
  equivalent to created_at order).

--------------------------------------------------------------------------------
3.2 GET /api/notifications/unread-count
--------------------------------------------------------------------------------
  Response:
    { "data": { "count": 3 }, "status": 200, "message": "Unread notifications count retrieved successfully." }

  This is a single indexed COUNT query, safe to poll on every app open.

--------------------------------------------------------------------------------
3.3 POST /api/notifications/{id}/read
--------------------------------------------------------------------------------
  Marks exactly one notification as read.
  Success: { "data": null, "status": 200, "message": "Notification marked as read." }
  If {id} does not exist, or exists but belongs to another user, or was already
  read (still counts as "not actionable" in the same sense): 404
    { "data": null, "status": 404, "message": "Notification not found." }
  (Marking an already-read notification read again is a no-op that still
  returns 200 as long as it's yours — 404 only fires for wrong id or wrong
  owner.)

--------------------------------------------------------------------------------
3.4 POST /api/notifications/read-all
--------------------------------------------------------------------------------
  Marks every unread notification of the calling user as read.
  Response:
    { "data": { "updated_count": 5 }, "status": 200, "message": "All notifications marked as read." }

--------------------------------------------------------------------------------
3.5 DELETE /api/notifications/{id}
--------------------------------------------------------------------------------
  Deletes one notification. Same ownership rule as 3.3 — 404 if not yours or
  does not exist.
  Success: { "data": null, "status": 200, "message": "Notification deleted." }

5. EXACT `type` VALUES AND `data` PAYLOAD KEYS PER NOTIFICATION
================================================================================

These are the literal strings currently produced by the 5 event listeners.
The `type` field on a notification list item and the `type` key inside its
`data` object always carry the same value (kept as two separate fields on
purpose: `type` is our DB column for filtering/history, `data` is what was
literally sent to Firebase — they happen to overlap today).

  type: "instructor_delegated"
    Audience: instructor
    data: { "type": "instructor_delegated" }
    No id in data. Suggested screen: open the instructor's own permissions/home
    screen — there is no single target entity to deep-link to.

  type: "treatment_completed_by_student"
    Audience: instructor
    data: { "type": "treatment_completed_by_student", "treatment_id": "<int>" }
    Screen: the treatment review screen for that treatment_id
    (GET /api/instructor/treatments/pending/{id} on the existing instructor API).

  type: "new_cases_available"
    Audience: student
    data: { "type": "new_cases_available" }
    No id in data (it's a broadcast to every student in the affected courses,
    covering possibly multiple new cases at once). Screen: the "available
    cases" browse screen, no specific patient pre-selected.

  type: "new_store_order"
    Audience: store owner
    data: { "type": "new_store_order", "order_id": "<int>" }
    Screen: that order's detail screen in the store dashboard.

  type: "diagnosis_reviewed"
    Audience: student
    data: { "type": "diagnosis_reviewed", "diagnosis_id": "<int>" }
    Fires for BOTH approval and rejection of a diagnosis the student suggested
    — the title/body text differs ("تمت الموافقة على التشخيص" vs "تم رفض
    التشخيص") but type and data shape are identical either way. If you need to
    distinguish approved/rejected programmatically rather than by reading the
    body text, tell us and we'll add a status key to data — it is not there
    today.
    Screen: that diagnosis's case detail screen.

  type: "treatment_reviewed"
    Audience: student
    data: { "type": "treatment_reviewed", "treatment_id": "<int>" }
    Same approved/rejected caveat as above — not distinguished in data today,
    only in the title/body strings.
    Screen: that treatment's detail screen.

  type: "order_status_updated"
    Audience: student
    data: { "type": "order_status_updated", "order_id": "<int>" }
    Screen: that order's detail screen in the student's purchase history.

  type: "general" (default)
    This is only a fallback value in the backend method signature for any
    future caller that forgets to pass a type. None of the 5 current listeners
    actually produce this — if you ever see it, treat it as "no specific
    screen, just open the notification list."

Every `data` value is a STRING (including numeric ids — e.g. "123", not 123).
This matches how FCM data payloads work (FCM data values are always strings on
the wire); we did not change that convention for the DB-stored copy either, so
`data` in the notification-history response has the same string-typed ids.
